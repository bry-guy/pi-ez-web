# Browser pi-sync refresh: minimal implementation plan

**Status:** Source at audit base `ffb5499` contains partial implementations;
unchecked acceptance criteria, including live credentialed CLI-to-web acceptance,
remain unverified.

## Goal and limits

An opened, visible, synchronized conversation should show settled remote changes automatically, usually within 20 seconds plus network/materialization time. This is snapshot refresh, not remote token streaming. Hidden tabs catch up on focus. Local conflicts require explicit user resolution. Keep JSON mode and pi-sync as the only authority for ETags, leases, fingerprints, and materialization.

Optimize for **one automatic check in pi-sync, one browser demand loop, and one host exclusion boundary**. Do not build a server observer platform or a second sync engine.

## 1. Reuse one conflict-aware pi-sync operation

Share the existing CLI idle poll's ETag/lease/idle check as an awaitable automatic-check operation with explicit automatic intent; retain CLI command-context dispatch where needed. The CLI's 20-second timer and the web request use that logic; the web host does **not** start another extension timer. Preserve the automatic local-divergence check before materializing or switching. Expose the operation through the existing extension-command bridge if practical (a narrow automatic mode/command), not by dispatching manual `/sync refresh`: today that command's fingerprint check runs only when `autoRefreshInFlight` is set. The web command bridge currently discards handler results, so forwarding a small unchanged/busy/conflict/refreshed outcome may need one narrow change; do not invent a callback framework. Do not use `/sync reconcile` as background refresh; keep extension errors observable.

**Proof:** real JSON-mode web-loaded extension: changed remote ETag refreshes, unchanged ETag and remote lease do nothing, local JSONL divergence is preserved, offline checks retry on the next demand, and repeated remote settlements still refresh. CLI behavior remains intact.

## 2. Make attachment passive and exclude local operations

`RealSupervisor._attach()` currently calls `PiSyncWebAdapter.beforePrompt()`, which runs `/sync reconcile`; merely attaching a selected conversation for observation must not reconcile or replace it. Move prompt preparation to actual prompt admission. Preserve its required lease/stale-session behavior, but do not let `beforePrompt()` silently reconcile to a different snapshot and then send the pending message; reject the stale expected snapshot before reconciliation or send, retaining the user's input. Verify the existing `/sync reconcile` path and that extension `session_start` does not introduce a conflicting write before the automatic check.

At the real session runtime, coalesce simultaneous tab checks and skip if a turn, compaction, bang command, or another refresh is active. Use the smallest shared exclusion boundary for refresh through replacement and local operation admission; prompt admission must be protected **before** SDK streaming becomes true, and bang must remain protected through execution and persistence. Recheck the current runtime before acting. Do not hold a lock needed for turn completion or abort, or build a generic mutation scheduler. Keep the manual refresh action available separately.

**Proof:** race refresh with prompt admission, bang persistence, and compaction; nothing is lost, no request deadlocks, and two tabs never materialize the same remote change twice. If a local mutation is not covered by the existing normalized-envelope fingerprint, block automatic replacement for that case; do not introduce automatic upload or a repository-wide eligibility framework.

## 3. One browser trigger and content update path

Use one helper for a visible, selected, enrolled conversation: check on selection, focus and reconnect, then every 20 seconds while visible. Skip offline, streaming/compacting, already-checking, or with pending composer text/attachments. Reuse `openTranscript()` and existing recovery after the server's automatic check. Consolidate the current `refreshActiveSync()` and selection-refresh behavior around this helper; do not add a second refresh loop. Manual `/sync` remains explicit.

The SSE hub broadcasts globally: apply `session_switched` navigation only if this tab still views its source. For a same-ID replacement, reload the content rather than reselect and reset the composer; for a different-ID replacement, guard selection. Capture active selection and composer state before awaiting, then recheck immediately before applying a response. Preserve text and attachments that appear mid-request; never silently retarget a send to a superseded snapshot. A second tab can replace the snapshot without changing the native session ID: affected prompt and bang writes must carry a narrow **expected-snapshot precondition**, using an existing trustworthy identity if available. Reject a mismatch before prompt preparation or bang execution, retaining the input. Client checks alone cannot close that race; no universal API generations or lineage journal are needed.

**Proof:** two tabs keep independent selection/drafts, typing mid-refresh is retained, stale expected-snapshot writes (including those entering `beforePrompt()`) are rejected before execution, and reconnect/focus reload the correct materialized transcript. Check that the normal materialized file can be resolved from existing pi-sync bindings after a server restart. If it cannot, add only the durable pointer needed for that failing case; ambiguity must preserve the original copy rather than guessing from title or timestamps.

## Cut and keep

Do **not** add per-tab server observers, renewal/expiry, cross-tab draft telemetry, a lineage journal/transaction framework, universal generation propagation, or parallel host/extension timers. Do **not** retire the legacy coordinator as part of this work: mock mode and tests still use it, while real production uses `PiSyncWebAdapter`. Keep extension UI, SSE buffering/recovery, project/workspace visibility, lease/conflict checks, and focused real-runtime tests. Retire legacy compatibility later only if its actual consumers are removed.

## Execution sequence and parallel ownership

**Phase 0 — agree contracts (one owner, before editing in parallel).** Write down the proposed extension automatic-check command and its outcome (`unchanged`, `busy`, `conflict`, `refreshed`); verify the extension command bridge can return it or identify the smallest change needed. Propose a distinct `POST /api/sessions/:id/sync/check` for automatic checks, leaving manual `/sync/refresh` semantics intact. Agree its result shape with the browser owner, including the current local session and an opaque snapshot identity where needed. Synchronized transcript responses expose that identity; affected prompt/bang writes send it back. The server compares it under the exclusion boundary before prompt admission or bang execution and rejects a mismatch with a structured `409 sync_snapshot_stale`, without consuming the user's input. Phase 0 must settle the token source, what happens when a synchronized write omits it, and how same-ID replacement invalidates it across reconnect/restart; never expose a file path. This is *replacement* identity, not a content hash that changes on normal streaming, steering, follow-ups, or ordinary transcript growth. Keep non-synchronized requests unchanged. If `beforePrompt()` could replace a snapshot after the initial comparison, prevent that replacement under the same boundary or revalidate after it and reject before submitting the message. Define who reserves the runtime through attachment, refresh/replacement, prompt admission, and bang persistence; do not block turn completion/abort. These names and fields are **proposals**, not existing APIs. Do not begin parallel edits until these contracts are agreed.

**Parallel wave — after Phase 0, three disjoint streams (isolated worktrees if separate implementers).** Keep shared files and tests with a single owner; do not split adapter/routes/supervisor among agents.

**Acceptance gate:** repeated settled CLI turns appear in an eligible visible tab within about 20 seconds plus request/materialization latency; unchanged ETags, remote leases and busy sessions do not replace; local divergence, drafts, prompts, bang and compaction are not lost; two tabs neither duplicate replacement nor navigate each other; stale same-ID writes reject before execution; focus/reconnect/restart show the correct materialized snapshot; web-to-CLI and CLI behavior remain unchanged. If a proof fails, fix that boundary before adding any of the excluded infrastructure.
